# COL7A1 audit — follow-up to FIX_NOTES_2026-04-18.md

**Date.** 2026-04-19
**Scope.** Trace the mechanism of the COL7A1 benchmark flip reported in
FIX_NOTES §"Benchmark delta" and determine whether the stated Fix #1
result ("86.7% → 100%") is a legitimate consequence of the capability
gate. This audit was flagged as a prerequisite for paper citation in
FIX_NOTES and in the project memory.

**Summary.** The headline "Fix #1 → 100%" conflates Fix #1 with three
prior scoring-related commits that were already in place at the time
the capability gate landed. Fix #1 directly resolves **three** of the
four previously-failing HDR cases (DMD, NF1, FBN1) via the variant-span
gate. The fourth (COL7A1, compound heterozygous) had already flipped
from PE top-1 to BE top-1 between the stored pre-fix benchmark (March 25)
and the immediate pre-Fix-#1 commit (`f113873`), purely through
changes in feasibility and consequence scoring. Separately, the
top-1 strategy chosen for COL7A1 ("Single-step Base Editing") addresses
only one of the two compound-heterozygous variants and is biologically
incomplete — the benchmark credits it via fuzzy substring matching
in the evaluator, not by substantive match to the "hybrid base editing
+ hdr" truth label.

**Recommendation.** Do not cite "86.7% → 100%" in the paper. The
honest claim is that Fix #1 resolves the three HDR-required
large-deletion failures (DMD, NF1, FBN1) pinned in
REVIEW_NOTES §4.1. The COL7A1 compound-het case is a separate
architectural gap that Fix #1 does not and was not designed to
address.

---

## 1. The case

`HDR_COL7A1_020` is a compound-heterozygous case with two 1-bp
transition variants in *COL7A1* (c.425A>G and c.2851C>T, disease
context: DEB). Both variants are single-base substitutions; neither
exceeds the PE_MAX_EDIT_SPAN_BP = 50 bp gate threshold. Truth label:

- **preferred:** `sequential hdr`
- **acceptable:** `hybrid base editing + hdr`
- **reject:** (empty)

Neither variant is gated by Fix #1 directly — the gate has no reason
to fire here.

## 2. What the stored benchmark files show

```
benchmark_results/v3_benchmark_results.json      (Mar 25, pre-Fix #1)
  HDR_COL7A1_020: top_strategy = "Single-step Prime Editing"
  top1_correct = False
  total: top-1 = 86.7% (26/30), top-3 = 96.7%

benchmark_results/v3_post_gate_results.json      (Apr 19, post-Fix #1)
  HDR_COL7A1_020: top_strategy = "Single-step Base Editing"

```

The *delta attributed to Fix #1* in the FIX_NOTES is 4 cases flipping
from incorrect to correct: DMD, NF1, FBN1, COL7A1.

## 2a. What re-running the benchmark on `f113873` (clean pre-Fix #1 baseline) shows

```
v3 benchmark at commit f113873 (immediate pre-Fix-#1):
  total: top-1 = 90.0% (27/30), top-3 = 100.0%
  HDR_COL7A1_020 top-1 = "Single-step Base Editing"  (already correct
                                                      per benchmark rules)
```

So between March 25 (`86.7%`) and the commit immediately before Fix #1
(`90.0%`), three unrelated scoring-related commits (`56750e9`, `959d2c0`,
`f113873`) independently flipped COL7A1 from PE top-1 to BE top-1 — a
+3.3pp benchmark lift that had nothing to do with Fix #1. Fix #1 then
adds the remaining three HDR-required cases (DMD, NF1, FBN1) for a
further +10.0pp lift to 100.0%. The honest attribution:

| Source | Cases flipped | Top-1 delta |
|---|---|---|
| Prior scoring commits (Mar 25 → `f113873`) | COL7A1 | +3.3 pp |
| Fix #1 capability gate (`f113873` → `74465ed`) | DMD, NF1, FBN1 | +10.0 pp |

## 3. What's actually true at `f113873` (the immediate pre-Fix-#1 commit)

Running the pipeline on commit `f113873` (the commit IMMEDIATELY
before Fix #1, without any additional changes) gives for
HDR_COL7A1_020:

```
rank  overall  feas   name
   1   0.9952  0.950  Single-step Base Editing
   2   0.9216  0.820  Single-step Prime Editing
   3   0.9216  0.820  Single-step Prime Editing
   4   0.9100  0.800  Single-step Base Editing
   5   0.8537  0.780  Dual Base Editing
   ...
```

**Top-1 is already "Single-step Base Editing" BEFORE Fix #1 is
applied.** The COL7A1 flip from PE top-1 to BE top-1 had already
occurred between the stored pre-fix benchmark (generated on Mar 25)
and the immediate pre-Fix commit (Apr 18 `f113873`). Commits between
those dates that touched scoring:

- `56750e9` — delivery-aware recommendations and SDSA sensitivity
- `959d2c0` — CLI pipeline / CDS-to-genomic mapping / UTR-aware annotation
- `f113873` — rank-stability / CLI editor-details

Any of these could have shifted BE's feasibility score above PE's for
this case. We did not trace which one; the key finding is that the
flip predates Fix #1.

## 4. What Fix #1 does and does not do

Direct effects of Fix #1 (span gate):
- `HDR_DMD_016` (180 kb): PE gated, HDR top-1. Legitimate fix.
- `HDR_NF1_017` (70 bp): PE gated, HDR top-1. Legitimate fix.
- `HDR_FBN1_022` (~8 kb): PE gated, HDR top-1. Legitimate fix.
- `HDR_COL7A1_020`: neither variant gated; **no direct effect**.

Not addressed by Fix #1:
- COL7A1 compound-het handling architecturally. The generator produces
  single-variant strategies for each of the two pathogenic alleles and
  ranks them independently. A strategy that addresses only 1 of N
  variants should be penalised for incompleteness; it currently is not.

## 5. The evaluator fuzzy-match issue (separate finding, same case)

Even accepting that "Single-step Base Editing" is the top-1 output for
HDR_COL7A1_020, the benchmark's `_strategy_matches` function at
`benchmarks/evaluator.py:128` flags this as correct because it
fuzzy-substring-matches "base" in the truth label "hybrid base editing
+ hdr":

```python
# benchmarks/evaluator.py:156-159
if "base" in ll and (
    "abe" in normalized or "cbe" in normalized or "base" in normalized
):
    return True
```

The intended truth label `hybrid base editing + hdr` means "BE on one
allele AND HDR on the other" — a multi-step strategy addressing both
compound-het variants. The pipeline output "Single-step Base Editing"
addresses only one variant. Biologically these are distinct; the
evaluator treats them as equivalent.

## 6. Proper claim for the paper

Replace the 86.7% → 100% headline with either:

**Conservative** (recommended): "Fix #1 improves top-1 accuracy
from 90.0% (27/30) to 100.0% (30/30) on the v3 benchmark by
resolving the three HDR-required large-deletion failures (DMD, NF1,
FBN1) that are directly addressed by the capability gate. The fourth
HDR-required case in the benchmark (HDR_COL7A1_020, compound
heterozygous) had already flipped to a benchmark-correct top-1 before
Fix #1, driven by unrelated scoring commits; moreover, the top-1
Single-step Base Editing strategy addresses only one of the two
compound-heterozygous variants and is biologically incomplete
despite being evaluator-credited. Compound-het completeness remains
an architectural gap separate from Fix #1."

**Do NOT** cite "86.7% → 100%" without that context — the 86.7%
baseline is from a stale benchmark (Mar 25) three commits before
Fix #1, and conflates the span-gate fix with earlier independent
scoring changes.

## 7. Remediation options (not blocking this audit)

### Option A — Just document (lowest effort)

Add the caveat to REVIEW_NOTES, FIX_NOTES, and paper draft. No code
changes. Appropriate if CRISPRArchitect architectural improvements
are out of the current work window.

### Option B — Tighten the evaluator match (narrow code change)

Replace the loose substring match in `_strategy_matches` with a
compound-het-aware test: when a case has ≥2 pathogenic variants,
"Single-step X" should NOT match a "hybrid" or "sequential" truth
label. Would require a new case-aware signature but scoped to the
evaluator only.

### Option C — Compound-het completeness penalty (architectural)

In the generator / scorer, flag strategies that address fewer than
all variants in a multi-variant case and apply a completeness penalty.
This is a bigger refactor and aligns with the "Compound-het handling"
remediation flagged in FIX_NOTES §"Related but distinct issue".

## 8. State after this audit
